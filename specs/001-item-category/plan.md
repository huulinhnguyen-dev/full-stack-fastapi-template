# Implementation Plan: Item Categories

**Branch**: `feat/add-category-to-item` | **Date**: 2026-11-23 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/001-item-category/spec.md`

## Summary

Users get personal categories, which they create and delete on a new Categories page. Each item can
optionally reference one of its owner's categories. The Items list gains a Category column, and
the add/edit item dialogs gain an optional Category picker. Deleting a category leaves its items
in place, uncategorized.

The technical approach:
- a new `category` table, owned per user, with a case-insensitive unique index on the name;
- a nullable `item.category_id` foreign key with `ON DELETE SET NULL`;
- a new `/api/v1/categories` router (list/create/delete, no superuser bypass);
- additive `category_id` / `category` fields on the item schemas;
- a regenerated frontend client.

Work is built backend first: model, migration, CRUD and API with tests, then client generation,
then UI and E2E tests.

## Technical Context

**Language/Version**: Python 3.14 (backend); TypeScript, strict mode (frontend)

**Primary Dependencies**:
- Backend: FastAPI ≥0.141, SQLModel 0.0.47 on SQLAlchemy 2.0.51 (research R1), Pydantic v2,
  Alembic ≥1.19
- Frontend: React, Vite, TanStack Router and Query, react-hook-form with zod, shadcn/ui (Radix
  `Select`), lucide-react
- No new dependencies.

**Storage**: PostgreSQL (psycopg 3), via Docker Compose service `db`

**Testing**:
- pytest + `TestClient` against real Postgres, with a coverage gate of 90% or more
- Playwright E2E against the Compose stack

**Target Platform**: Linux containers (Docker Compose); modern desktop browsers

**Project Type**: Web application (FastAPI backend and React SPA served by FastAPI)

**Performance Goals**: The Items list (100 items) with categories renders within 2 seconds
(SC-006). The list endpoint adds at most one extra query (`selectinload`).

**Constraints**:
- Additive, backward-compatible API changes
- Zero data loss for existing items (FR-013)
- Categories are private per user, with no admin exception (Clarifications Q1)

**Scale/Scope**:
- New: 1 table, 3 endpoints, 1 page
- Changed: 4 item endpoints, 2 item dialogs, 1 table column
- Tens of categories per user expected; the list uses the existing `skip`/`limit` paging

There are no open questions; every decision is resolved in [research.md](./research.md).

**Terminology**: "administrator" in the spec means a user with `is_superuser = true`, which the
code and tasks call a "superuser".

## Implementation Order (Principle I)

1. **Backend data**: models and schemas in `models.py`, plus the Alembic migration. Verify
   upgrade/downgrade (quickstart §1).
2. **Backend logic and API**: `crud.py`, `routes/categories.py`, `routes/items.py` changes, router
   registration.
3. **Backend tests**: CRUD and API tests, conftest teardown, coverage ≥90% (quickstart §2).
4. **Contract handoff**: regenerate the frontend client and commit it (quickstart §3).
5. **Frontend**: Categories page and sidebar, `CategorySelect`, item dialogs, Category column.
6. **E2E tests**: `categories.spec.ts` and the `items.spec.ts` additions (quickstart §5).

Within each user story in `tasks.md`, backend tasks MUST come before frontend tasks.
